# 抽奖小程序与收银系统立减券联动

日期：2026-09-18
状态：历史设计记录（0.6.2 阶段）。0.7.0 已实现券管理、独立券服务和扫码核销，请以同目录《券管理与小程序接入-0.7.0.md》为当前功能、接口及部署说明。
用途：保留最初需求和设计推导。以下“尚缺少”等表述是当时状态，不代表当前版本；正式云部署和真实小程序接入仍未完成。

## 1. 目标与边界

消费者在小程序抽奖获得一张店铺抵扣券，出示券码；收银员扫码后，购物车出现独立优惠行，应收金额减少；付款成功后，云端把该券标记为已使用，小程序同步展示，任何设备都不能再次使用。

示例：商品应收 50 元，使用 10 元券，购物车展示“抽奖立减券 -10 元”，向收钱吧提交收款 40 元。券码和顾客支付用的付款码是两个不同的码，先扫券，再进入付款流程扫付款码。

本方案是商家自行承担优惠的店铺抵扣券，不是充值余额、现金红包，也不代表微信或收钱吧会补贴券面额。
若实际需求是微信支付官方代金券、微信卡包商家券或平台立减金，必须先确认具体产品、商户权限和支付渠道支持情况，不能直接套用本方案。

## 2. 当前收银系统已有和缺少的能力

已核对源码：

- 能接收普通商品条码和本地优惠券条码，不限于 69 开头。
- 优惠券可作为独立负金额行加入购物车，每单最多一张，不扣商品库存。
- 先计算单品优惠，再抵扣券；抵扣不超过应收，订单不会成为负金额。
- 已有收钱吧支付结果核验、重复收款保护、订单库存处理及退款优惠分摊。

尚缺少：外部券码识别、云端验券、唯一券实例、跨收银机锁券、一次性核销、释放与异常补偿。
目前本地优惠券本质上是可反复使用的优惠配置，不是中奖用户各自持有的一次性奖品。单纯导入一批券码，不能解决两套系统的数据同步和重复使用。

相关代码位置：`src/App.jsx` 的 `scanBarcode`、`addLineToCart`、`beforeSqbStart`、`applySqbRecord`；`src/orderLogic.js` 的 `priceOrder`、`reconcileStock`；`src/afterSales.js` 的优惠分摊。
现有未知条码会进入商品新增，需要新增外部券码识别分支；外部券也不能直接当作不存在于本地商品库的普通商品传入库存校验。

## 3. 推荐架构

```text
抽奖小程序 -> 抽奖/优惠券云后台 + 数据库 <- 收银本机服务 <- 网页/Windows/Mac
                                            |
                                            v
                                          收钱吧
```

- 建议小程序团队负责唯一的优惠券云后台，可使用已有后端、云函数或云托管，无需为本方案重写抽奖系统。
- 小程序负责领券与展示；云后台是券规则、状态和核销记录的唯一权威来源。
- 收银端通过本机支付服务调用云端 HTTPS 接口，不让前端页面直接持有核销管理密钥。
- 此联动本身不要求收银电脑有固定公网 IP，也不要求公网访问这台电脑；收银服务主动访问稳定的云端接口即可。支付渠道自身的网络要求另行遵守。
- 两边需要联网。云端不可用时，不允许先按外部券优惠结账再事后补查；顾客可选择移除券、按明确确认后的原应收金额付款。
- 不要求两边使用相同编程语言、相同 AI、同一个数据库，也不要求把整套商品库存搬到云端。

## 4. 小程序及云后台负责什么

1. 中奖确认和发券由服务端执行；同一中奖记录重试不能重复发券，券发放与中奖记录建立唯一关联。
2. 每张券有唯一 `coupon_id`，不同消费者抽到同面额券也必须有不同券码。
3. 券面额、适用商户/门店、有效期、消费门槛、适用商品及叠加规则由服务端保存和校验，不能信任二维码里写的金额。
4. 使用不可预测的高随机性券码，不能把顺序流水号、手机号、用户 OpenID 或“10元”直接作为可核销凭证。
5. 提供正常二维码或 Code 128 条形码，内容为约定的券令牌，如 `LJC1_<随机标识>`。不要用只能打开小程序页面的小程序码代替核销码。
6. 提供“可用、使用中、已使用、已过期、已作废”等页面状态。每次进入券详情向服务端查询，使用中可定时刷新；只修改本地页面并不算核销。
7. 提供下文的锁定、支付准备、核销、释放、查询等接口，使用数据库事务/条件更新避免两台收银机同时占用同一张券。
8. 为收银设备提供独立、可撤销的接口凭证，限制到对应商户/门店与核销权限；发券权限与核销权限分开。
9. 有核销记录和异常处理入口，能按券号、收银订单号、支付流水查询，具备数据库备份和访问限流。

小程序客户端不保存核销管理密钥、微信 AppSecret 或收钱吧签名私钥。收银系统也不需要获得消费者的微信账号密码。

## 5. 收银系统需要新增什么

1. 扫描路由：区分商品码、本地优惠券、外部中奖券和付款码。外部券在购物车阶段处理，不能当成新商品；在收款阶段误扫券码时应提示返回用券，不调用收钱吧。
2. 自动验券和锁定：扫描后调用云后台，只有原子锁定成功才加入优惠行，展示券名、面额、实际抵扣和状态。不能先减价再异步校验。
3. 保留每单最多一张的限制，本地券和外部券合计最多一张；已锁定同一张券再次扫描只提示已添加，不能重复减价。
4. 为购物车建立稳定的结算会话 ID；云端锁定绑定这次结算和收银设备。挂起、刷新、订单生成后不能随意换 ID 导致锁丢失或产生重复核销。
5. 修改商品数量、单品优惠、移除商品后重新校验用券金额和门槛；付款前获取最终确认并冻结商品、优惠与支付金额。
6. 发起收钱吧扣款之前，将券切换为不可自动释放的支付占用状态；服务端确认授权成功后才允许发起扣款。
7. 根据本机后端已验签的收钱吧成功记录提交核销。保存券 ID、核销 ID、面额、实际抵扣、活动 ID、本地订单 ID、收钱吧订单和支付流水映射。
8. 移除券、取消未支付订单时释放券；挂起订单的用券处理按第 8 节执行。明确的付款失败允许释放，支付状态未知不能释放。
9. 已付款但核销接口超时：不重新收款，不释放券，不只弹出错误就结束。后端保存待核销任务，重启后查询并使用同一请求 ID 重试，异常项可人工核对。
10. 券抵扣后实付为 0 的订单走确认零元结算，不向收钱吧发起 0 元扣款；订单确认出库时仍须完成一次券核销。手动“0元出库”则不应消耗中奖券。
11. 流水与导出支持区分商品收入、券面额、券实际抵扣及支付实收，退款按原单优惠分摊后的实际支付金额计算。
12. 网页、Windows、Mac 共用这套逻辑和后端能力；旧版本未接入前不能通过手工输入相同券码冒充完成核销。

## 6. “扫过失效”的正确处理

建议采用以下状态，而非一读到码就永久销毁奖品：

```text
可用 AVAILABLE
  -> 扫码成功：锁定 RESERVED，其他订单不能使用，小程序显示“使用中”
  -> 付款前确认：支付占用 PAYMENT_PENDING
  -> 已确认收款或零元订单完成：已使用 REDEEMED

RESERVED -> 移除券/取消未付款交易/安全的锁超时 -> AVAILABLE 或 EXPIRED
PAYMENT_PENDING -> 只有确认未扣款且本笔支付终结，才能释放
```

- 扫码瞬间即禁止其他订单使用，满足防止重复使用的目的。
- 永久核销以订单完成为准，避免扫码后顾客取消购买却损失奖品。
- 未开始支付的购物车锁可约定较短超时；进入支付流程或支付结果未知的锁，不能简单超时自动解锁。
- 锁续期与支付准备必须检查当前锁持有者和版本；旧锁失效后，原设备不能拿过期授权继续收款。
- 同一张券即使被截图，核销后仍不能再次使用；但静态券码本质上可能被先持有截图的人抢用。若要求“只能中奖本人使用”，需要另外实现短时动态码或小程序内确认，不能仅凭唯一券号声称已验证本人身份。

## 7. 双方统一的接口约定

以下为建议的自定义业务接口，不是微信或收钱吧现成接口，也不是已实现的路由。

| 功能 | 示例接口 | 必须保证 |
| --- | --- | --- |
| 验券并锁定 | `POST /v1/coupon-reservations` | 查询规则、校验资格和占用在同一原子操作完成；返回券信息、锁 ID、版本、实际抵扣与有效时间 |
| 调整购物车/续期 | `POST /v1/coupon-reservations/{id}/revalidate` | 只允许当前持有者操作，重新核算优惠；修改后的旧报价失效 |
| 支付前确认 | `POST /v1/coupon-reservations/{id}/prepare-payment` | 绑定最终订单、金额和版本，进入支付占用；失败时禁止扣款 |
| 确认核销 | `POST /v1/coupon-reservations/{id}/commit` | 只接受授权收银后端的可信交易结果；同一订单重试返回原结果，不二次核销 |
| 取消占用 | `POST /v1/coupon-reservations/{id}/release` | 不能释放他人锁或已核销券；支付未知不能释放 |
| 查询结果 | `GET /v1/coupon-reservations/{id}` | 返回权威状态，接口超时后先查状态；不能把超时当作业务失败 |

公共约定：

- HTTPS + JSON，接口版本固定，测试与正式环境、凭证、券码分离。
- 金额一律用整数“分”：10 元传 `1000`，不能在接口中混用元和分。
- 时间为带时区的 ISO 8601，资格校验使用服务端时间，不依赖收银电脑或手机的本地时钟。
- 请求携带 `merchant_id`、`store_id`、`terminal_id`、稳定的 `checkout_id`/`order_id` 和 `request_id`。
- 同一个业务动作重试复用 `request_id`；同 ID 但内容不同必须拒绝，而不是悄悄覆盖。
- 锁返回 `reservation_id`、不可伪造的授权凭证和版本；绑定订单及报价，不能挪到另一笔订单。
- 最终记录区分 `coupon_id`、`face_value_cents`、`discount_cents`、`goods_amount_cents`、`paid_amount_cents`、`redemption_id` 和支付流水，不能仅凭“金额一样”关联交易。
- 必须明确错误码，例如：不存在、过期、作废、已使用、被其他订单占用、不满足门槛、门店不匹配、版本过期、服务暂不可用。
- 终端身份鉴权与防重放由后端负责。前端传入 `paid: true` 不能作为收款成功证明；收银后端应依据已验签支付记录发送经过鉴权、绑定金额和订单的结果。是否还需云端独立查单由双方在安全评审时确定。
- 核销任务与支付结果要有持久化关联，不能依赖浏览器页面一直开着。两个独立系统不能假设靠一次网络请求就能完成跨系统原子事务。
- 不在普通日志、URL 查询参数和经营导出中暴露完整可用券令牌、接口密钥或消费者付款码；记录券 ID 和必要的脱敏标识即可。

建议双方先交付 OpenAPI 或等价的完整请求/返回样例，再分别写业务逻辑。

## 8. 需要商家确认的规则

| 问题 | 当前事实或首版建议 |
| --- | --- |
| 每单几张券 | 沿用已有要求：最多一张，含本地券和外部券 |
| 优惠顺序 | 建议沿用当前先单品优惠、后券抵扣；需确认是否允许与所有促销叠加 |
| 券面额超过应收 | 建议抵扣到 0、不找零、不留余额，实际抵扣与面额分别记账，并在领券规则中说明 |
| 有无门槛与适用商品 | 待确定；首版可做全场券。限制商品时需约定两端统一 SKU/条码，不用各电脑的本地随机商品 ID |
| 扫码后取消购买 | 建议释放，券有效期未过则可再次使用 |
| 未结账挂单 | 建议释放外部券，保留券引用为“待重新验券”；取回挂单不能直接沿用旧优惠 |
| 退款是否退券 | 待确认。首版可不自动退券；若需要，应在退款确认后走独立、有审计且幂等的退券/补发流程 |
| 部分退款 | 只退对应商品分摊后的实付，不把券面额退成现金；不因部分退款直接恢复整张券 |
| 手动 0 元出库 | 建议移除/释放外部券，不把赠送出库算作中奖券核销 |
| 不同人使用截图 | 待确认是否允许转赠；不允许则增加动态码或本人确认流程 |
| 付款结果未知 | 保持占用并核对交易，不自动退券，不引导顾客重复付款 |
| 使用期限边界 | 建议支付准备时再次验有效期；已获授权并开始支付后不因跨过到期时间释放，等待该笔交易终结 |

以上建议尚未代替商家做最终业务决定。

## 9. 联调前小程序团队提供的材料

1. 确认券类型：自发店铺券，还是微信支付官方产品。
2. 现有技术栈和部署方式，是否已有后端、数据库或云开发环境。
3. 测试环境的 HTTPS API 地址、接口文档、鉴权方式与错误码；密钥通过安全渠道交付，不写入共享需求文档。
4. 至少一组未使用、已使用、过期、已作废和占用中的测试券，以及正常二维码/条形码图片。
5. 券面额、门槛、有效期、适用门店/商品、叠加、取消和退款规则。
6. 同一张券如何查询状态、超时后怎样查询操作结果、锁定和核销怎样实现并发唯一性。

收银团队提供：0.6.2 当前订单与优惠数据结构、门店/终端标识约定、支付状态与流水字段、三端联调版本及测试记录。无需把收钱吧私钥交给小程序前端。

## 10. 上线验收清单

- 50 元订单使用 10 元券，购物车减 10 元、收钱吧仅收 40 元，后台券状态为已使用，流水能对上。
- 同一张券连续扫描不重复减价；两台收银机同时扫描，最多一台成功占用。
- 不同券码在同一订单不能叠加；同一券码在另一订单已使用后不能再用。
- 伪造、篡改金额、过期、作废、越门店和过期锁授权全部被拒绝。
- 取消未付款订单后，在有效期内能重新使用；挂单取回必须重新验券。
- 修改商品与优惠后，门槛和抵扣额正确重算；已开始付款不能再改金额。
- 支付结果未知或网络断开时，券不会被其他订单占用，原设备不会再次收款。
- 支付成功但核销响应丢失、进程退出或重启后，能查询并补偿，最终只有一次核销和一笔收款。
- 0 元结算可正常核销、扣库存；手动 0 元出库不消耗中奖券。
- 退款不超过分摊后的实付金额，退券/不退券符合已确认规则。
- 网页、Windows、Mac 使用同一张测试券互相验证状态，不能各自独立核销。
- USB 扫码盒能读取实际手机屏幕上的券码，输出内容完整，结束符与系统一致。

首轮使用测试券和模拟支付联调。真实收款测试须另行确认商户、金额和资金去向。
