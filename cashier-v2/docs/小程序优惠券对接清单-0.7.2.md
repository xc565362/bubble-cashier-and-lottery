### 业务边界先约定

这是 **商家自己承担优惠的店铺立减券**，不是微信官方立减金、现金红包或平台补贴。优惠只在本收银系统的商品订单中抵扣，不能提现、不找零；退款不自动退券。

扫码后立刻锁定该券，其他订单不能同时使用；但只有核实付款成功或完成零元结算才永久核销。未付款正常取消应释放，不能简单“扫一下就永久作废”，否则顾客未买也会损失券。

# 02 券中心部署与收银连接

### 给部署同事的参考步骤

使用发行包 **coupon-service-0.7.2.zip**，或源码中的 coupons 目录。需 Node.js 24 LTS；SQLite 使用 Node 内置支持。以下命令是部署示例，未在你的云环境执行。

在解压后的根目录运行，当前目录必须能看见 **coupons/**：

```bash
docker build -f coupons/Dockerfile -t cashier-coupons:0.7.2 .
docker run -d --name cashier-coupons --restart unless-stopped \
  -p 127.0.0.1:3910:3910 \
  -v cashier-coupon-data:/data \
  --env-file /secure/coupon-production.env \
  cashier-coupons:0.7.2
```

Dockerfile 的 COPY 使用父目录上下文，不能用 `docker build ... ./coupons` 替代。云托管不一定允许直接运行以上命令，应按平台转换构建和持久卷配置。

| 配置 | 要求 |
| --- | --- |
| COUPON_ADMIN_TOKEN | 私密随机值，32-300 字符，允许字母、数字、下划线、点、连字符 |
| COUPON_ENV | 正式为 production；开发库不能直接混用 |
| COUPON_DATA_DIR | 容器为 /data，挂真实持久卷且限制读取权限 |
| HOST / PORT | 容器 0.0.0.0 / 3910；外部通过 HTTPS 反向代理 |

反向代理将专用 HTTPS 域名根路径转发到服务，设置超时、请求体大小和频率限制，不把明文 3910 暴露公网。`GET /healthz` 仅存活检查；还需认证接口确认正式环境与中心身份。

### 部署后在收银端操作

1. **券管理 → 云端连接**，输入正式 HTTPS 源站域名和管理密钥。域名不附加 /v1、账号密码、查询参数等。
2. 检查正式中心身份和环境，再创建正式券活动。开发环境的活动和券不自动转成正式券。
3. **小程序接入 → 新建接入凭证**，只授权所需活动，把该抽奖后台凭证安全交给同事。
4. 各收银设备分别连接该中心，获得设备专属收银凭证；不要复制连接文件导致设备身份重复。

管理密钥、抽奖后台凭证、收银终端凭证用途不同。小程序只用抽奖后台凭证，并且仅放在可信后端。当前本地管理页面没有员工角色隔离，收银电脑访问需另行管理。

# 03 小程序同事要改哪里

### 后端：在确认中奖后发券

1. 用微信登录上下文获取可信用户身份，不接受前端随意传来的 owner / openid。
2. 抽奖资格、奖品和中奖记录必须由后端确认并保存。用户不能自己声明“中了 20 元券”。
3. 从已保存的中奖记录取稳定 ID 作为 awardId；取对应正式 campaignId。按活动配置决定面额，发券请求不传用户自定金额。
4. 调用发券接口，将返回的 couponId 关联到该中奖记录。网络失败记为待发券并重试原记录，不能重新抽一次或换 awardId 反复领券。
5. 券列表 / 详情也从后端校验当前用户再请求；只向前端映射它需要的字段，不透传管理信息或凭证。

### 推荐使用现成服务端 SDK

文件：`coupons/lottery-client.cjs`。示例运行在可信 Node.js 后端；下列 verifiedAward、authenticatedOwner 都必须已从服务端认证 / 数据库校验取得，不是直接读取用户请求体。

```js
const { createLotteryClient } = require('./lottery-client.cjs');
const client = createLotteryClient({
  baseUrl: process.env.COUPON_URL,
  token: process.env.COUPON_LOTTERY_TOKEN,
  campaignId: process.env.COUPON_CAMPAIGN_ID,
});
const coupon = await client.issueForVerifiedAward({
  owner: verifiedAward.owner,
  awardId: verifiedAward.id,
});
const wallet = await client.listForAuthenticatedOwner(authenticatedOwner);
const detail = await client.detailForAuthenticatedOwner(
  authenticatedOwner, couponId
);
```

SDK 自动生成稳定发券请求编号；调用超时为 12 秒。配置 URL 必须是 HTTPS 源站。请求失败时做有限次数退避重试，保留相同中奖 ID，不另发新券。

### 前端：给顾客看得懂的券包

中奖结果页显示券面额 / 门槛 / 有效期，提供“查看我的券”；券包列出各券状态。仅 AVAILABLE 详情返回的 code 可生成可用二维码。二维码页回到前台应刷新状态，展示期间做限频刷新；使用中、已使用、过期或作废时停止展示可用码。

不要把手机端倒计时当作核销依据，不允许前端直接调用发券、作废或核销接口。券接口会拒绝带 Origin 的浏览器直连请求；正确链路始终是前端 → 可信后端 → 券中心。

# 04 接口契约与券状态

请求头：`Authorization: Bearer <抽奖后台凭证>`；POST 同时使用 `Content-Type: application/json`。凭证需授权对应活动。

### 三个小程序后台接口

| 接口 | 输入 | 关键输出 / 限制 |
| --- | --- | --- |
| POST /v1/coupons/issue | requestId、campaignId、owner、awardId | 同中奖记录幂等发券，只有可用券返回 code |
| GET /v1/coupons | owner、page；SDK 同时传 campaignId | items / page / total / pageSize，分页 30；列表无 code |
| POST /v1/coupons/detail | id、owner | 校验归属；可用券详情可取 code，归属不符拒绝 |

```json
{
  "requestId": "stable-award-request-id",
  "campaignId": "configured-campaign-id",
  "owner": "server-verified-user-id",
  "awardId": "persisted-winning-record-id"
}
```

示例值是占位文字，不是可直接用于正式发券的参数。成功返回 `{"ok":true,"data":...}`；失败返回 `{"ok":false,"code":"...","error":"..."}` 和相应 HTTP 状态码。金额为整数分，日期为 ISO 8601。字段包含 id、name、amountCents、minimumCents、startsAt、expiresAt、state。

同 requestId 改内容会冲突；同一活动授权范围内，中奖 ID 不能换用户重复发券，轮换凭证不重置幂等性。默认每凭证每分钟 180 请求；容量需按活动规模压测，遇到 429 应退避，禁止前端高频轮询。

### 状态展示

| state | 顾客显示 | 能否当作可用券 |
| --- | --- | --- |
| AVAILABLE | 可使用 | 仍需满足生效时间、门槛等校验 |
| RESERVED | 正在收银台使用 | 否 |
| PAYMENT_PENDING | 付款结果核实中 | 否 |
| REDEEMED | 已使用 | 否，退款也不自动恢复 |
| EXPIRED | 已过期 | 否 |
| VOID | 已作废 | 否 |

唯一券码形如 LJC1_...，是随机签名的持券凭证。可防重复使用，但不能阻止顾客转发截图后被别人先用。本版未开发动态短时二维码、柜台实名校验或自动退券重发。

# 05 交易、异常与数据边界

### 收银侧的生命周期

1. 加商品 → 扫中奖券 → 中心检查有效性和门槛 → 占用成功并显示抵扣。
2. 移除券或正常取消未付款交易：释放占用。仅占用、尚未准备支付的券，15 分钟后在后续访问时可释放。
3. 发起支付后进入付款待核实，不按上述超时自动释放。结果未知时仍锁住，不允许再次使用。
4. 收钱吧验签核实成功后保存订单、处理库存并核销券；零元订单走确认零元结算和持久化重试流程。
5. 已收钱但券同步暂时失败时保留待同步记录重试，不能再扣钱或自行把券改回可用。

### 运营规则

每单最多一张券，不与本地优惠券商品叠加；门槛按单品优惠后的金额判断，最多抵到 0 元。含中奖券不能直接挂单，先移除释放后再挂。正金额中奖券订单只走收钱吧确认收款。

已发券的面额、门槛和有效期不因修改活动自动改变；需要新条件就新建活动。暂停活动只停止继续发券，不等于所有已发券失效。作废需针对允许作废的券操作并记录原因，不能用作废解除不明支付。

### 三个库不是一个库

| 数据 | 保存位置 | 是否多机共享 |
| --- | --- | --- |
| 商品、库存、订单 | 各收银端本地存储 | 否，券中心不会同步这些数据 |
| 商户签名配置与支付恢复记录 | 各端私有目录 | 不应公开共享，用内置迁移 |
| 活动、中奖券、占用 / 核销状态 | 唯一正式云端券中心 | 是，各端访问同一中心 |

SQLite 需单实例、单持久数据目录；不能开多个各存一份库的副本，也不能用网盘同步数据库文件冒充共享。扩容到多实例或云函数时需适配数据库事务与唯一约束。

### 备份与恢复责任

云端维护人定期做 SQLite 一致性备份，或停止服务后备份完整私有数据目录；不要在线只拷主 sqlite 文件。目录内含签名材料，需加密和限制读取。

恢复旧券库可能让已用券看起来未用，必须先停发券 / 停用券，结合订单与支付记录对账后再营业。收银经营备份不包含云端券库；迁移电脑也不要回滚云端库。本机 coupon-connection.json 与 coupon-transactions.json 不得在未决交易时删除。

# 06 联调验收与交付顺序

### 建议顺序

提供云资料 → 确认持久化方案 → 部署唯一正式券中心 → 收银端连接 → 创建正式活动和后台凭证 → 小程序后端发券 → 券包二维码页面 → 双方真实设备联调 → 负责人签字上线。

### 每项均需留下实际结果

| 场景 | 通过标准 | 结果 |
| --- | --- | --- |
| 登录与中奖资格 | 未中奖不能伪造领奖，用户不能查别人券 | □ |
| 重试与并发发券 | 同一中奖记录始终只有一张券，换用户失败 | □ |
| 凭证权限 | 前端无密钥，抽奖凭证不能执行管理 / 核销 | □ |
| 两台同时扫码 | 同一券只有一台成功占用 | □ |
| 正常取消 | 未付款移除券后可在另一单重新使用 | □ |
| 真实实收 | 折后金额、商户到账、订单、库存、券核销一致 | □ |
| 支付未知 / 断网 | 不放券、不重收，重连后按原交易收敛 | □ |
| 零元订单 | 不调用零元扣款，核销和库存只发生一次 | □ |

| 退款 / 换货 | 按实际支付分摊，券不会自动恢复 | □ |
| 服务 / 收银端重启 | 状态持久保留，未完成同步能恢复 | □ |

真实收款和退款会涉及资金，必须由负责人明确知情并操作；联调使用专门样本和明确金额。生产模式收钱吧不应搭配开发环境券中心。Mac、不同 Windows 设备、实际扫码盒需要分别验收。
