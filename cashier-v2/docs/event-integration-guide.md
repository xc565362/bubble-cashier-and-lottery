# 活动接入指南（bubble-event/1 协议）

日期：2026-10-19
读者：运营、店长、活动开发同学。**不需要任何背景知识**，按顺序照做即可。

---

## 1. 这个协议是什么

以前收银台每接一个新活动（抽奖、打卡、集点……）都要改收银台代码、重新发版。

`bubble-event/1` 是一套约定：**只要活动服务器按这套约定提供接口，收银台就能直接接入，一行收银台代码都不用改。**

- 活动服务器：你们为活动搭建的小服务（例如现有的抽奖服务器），负责发奖、存记录、核销。
- 收银台：店里的收银系统。它通过"地址 + 工作人员密钥"连接活动服务器。
- 一个收银台可以同时连接多个活动，互不干扰。

## 2. 在收银台接入一个活动（3 步）

前提：活动服务器已经在运行，并且你手上有两样东西（找活动开发同学要）：

1. **服务地址**，例如 `https://events.example.com`（或本机测试用 `http://127.0.0.1:8787`）；
2. **工作人员密钥**（一串字符，相当于收银台的通行证，注意保密）。

操作：

1. 打开收银台的 **活动** 页面；
2. 把 **服务地址** 和 **工作人员密钥** 填入连接表单，点 **连接**；
3. 看到活动出现在列表里（显示活动名、地址、支持的功能）就是成功了。

连接时收银台会自动做三件事验证，全部通过才会保存：

- 检查地址是否合法（必须是 HTTPS；只有本机服务才允许 `http://127.0.0.1`）；
- 读取活动服务器的 **协议清单**（`GET /api/manifest`）并严格校验格式；
- 用密钥做一次"假查询"（查一个全 0 的核销码，服务器应回答"未找到"）来确认密钥有效——不会碰任何真实中奖记录。

密钥在收银台里 **加密存储**（AES-256-GCM，密钥文件独立保存），任何界面和接口都不会回显明文。

要换掉某个活动：在活动列表里 **移除** 即可；密钥轮换后用新密钥重新连接一次（同一名称的活动会覆盖旧连接）。

> 注意：有未完成的收退款或券占用时，不能连接/移除活动，请先完成当前交易。

### 部署时用命令行连接（可选，免界面操作）

服务器上部署收银服务时，可以用一次性脚本完成连接，不在浏览器里输入密钥：

```bash
EVENT_BASE_URL=https://events.example.com EVENT_STAFF_KEY=工作人员密钥 \
  BUBBLE_ONLINE_DATA_DIR=/var/lib/bubble-online BUBBLE_ONLINE_KEY_FILE=/etc/bubble-online/key \
  node scripts/provision-event.cjs
```

脚本走的就是界面上"连接"的同一套校验（地址 → 协议清单 → 密钥探测），成功后把加密连接直接写入数据目录并打印活动名称。失败会打印原因并以非零码退出。

## 3. 连接后，收银台上每个按钮干什么

| 功能 | 协议动作 | 在收银台的效果 |
| --- | --- | --- |
| 查券 | `lookup` | 扫/输入顾客核销码，立刻看到中的是什么奖、是否已核销、中奖者（脱敏）。**不产生任何改动。** |
| 核销 | `redeem` | 把该核销码标记为"已核销"并发放奖品。每个码只能核销一次，重复核销会被拒绝。 |
| 实时记录 | `records` | 查看该活动全部中奖记录和汇总（总数、待核销、已核销、库存余量）。 |
| 导出 | `export` | 导出该活动全部记录为 CSV 文件，用于对账、复盘。（管理员权限） |

连接、移除需要管理员权限；查券、核销、实时记录收银员即可使用。

## 4. 现金类奖品怎么自动抵扣

活动协议清单里有一节 `benefits`，逐个奖品标明是实物（`physical`）还是现金权益（`cash`，含面额 `amountCents`，单位：分）。

现金权益的抵扣**不需要收银员手工算**：

1. 顾客中奖后，活动服务器会把现金奖发成收银系统券中心的一张 **立减券**，券码就是中奖核销码；
2. 结账时收银员扫顾客的核销码，购物车自动出现一行优惠（例如"抽奖立减金 -10 元"），应收金额随之减少；
3. 规则：先算商品优惠再抵扣券、每单限一张、抵扣不超过应收、不找零；
4. 付款成功后券被正式核销，不能再次使用；未付款取消会释放券。

实物奖品（帽子、购物袋等）不抵扣金额，核销后现场发放即可。

## 5. 故障排查

| 收银台提示 | 常见原因 | 怎么办 |
| --- | --- | --- |
| 请输入有效的活动服务地址 | 地址没填或格式不对 | 找活动开发同学确认完整地址（含 https://） |
| 活动服务地址须为 HTTPS | 用了 http 的非本机地址 | 线上服务必须 HTTPS；本机测试才允许 http://127.0.0.1 |
| 无法连接活动服务 | 服务没启动、端口不对、网络不通 | 确认服务已启动；本机默认端口 8787 |
| 活动服务未提供协议清单 | 服务版本太旧，不支持 bubble-event/1 | 让开发同学升级活动服务器 |
| 活动服务协议清单格式异常 | 清单字段不合规 | 把本文第 7 节的提示词发给开发同学核对 |
| 活动服务协议清单缺少 lookup 动作 | 服务没实现查券接口 | 同上 |
| 工作人员密钥无效 | 密钥填错、多余空格、已轮换 | 重新核对密钥；必要时重新连接 |
| 活动服务校验失败 | 服务器对探测请求返回了异常 | 让开发同学看服务日志 |
| 未找到此活动的核销码 | 码输错，或该码属于别的活动 | 核对后再扫；确认扫的是本活动的码 |
| 此奖品已核销 | 重复核销 | 属正常拦截，不要重复发奖 |
| 核销码格式不正确 | 扫码带入异常字符 | 手工输入核对 |
| 活动尚未连接 | 活动被移除或从未连接 | 重新连接 |
| 此活动服务不支持导出 | 该活动清单未声明 export | 用活动自己的后台导出 |
| 请先完成当前收退款和券占用 | 有挂起交易 | 先完成/取消当前交易再操作 |

# 协议规范（bubble-event/1）

## 1. 协议清单（无需鉴权）

GET /api/manifest → 200，Content-Type: application/json，直接返回清单对象（不要包 {ok,data} 外壳）：

{
  "protocol": "bubble-event/1",        // 必须是这个字符串
  "service": "my-event-2026",          // 服务标识：1-64 个可打印字符，无控制字符；收银台用它作为连接 id
  "version": 1,                        // 必须是数字 1
  "display": {
    "title": "活动显示名",              // 1-60 字符
    "recordFields": [                  // 1-12 项，收银台据此渲染记录列表；key 须匹配 /^[A-Za-z][A-Za-z0-9_]{0,30}$/ 且不重复
      { "key": "code",      "label": "核销码", "type": "code" },
      { "key": "prize",     "label": "奖品",   "type": "text" },
      { "key": "status",    "label": "状态",   "type": "enum", "values": ["pending", "redeemed"] },
      { "key": "createdAt", "label": "时间",   "type": "timestamp" }
    ]
    // type 只能是 code / text / enum / timestamp；enum 必须带 1-20 个非空字符串 values
  },
  "benefits": {                        // 可选；按奖品 id 声明权益类型
    "cap":    { "kind": "physical" },
    "cash10": { "kind": "cash", "amountCents": 1000 }   // amountCents 单位：分，非负整数
  },
  "actions": ["records", "lookup", "redeem", "export"]  // 必须是这四个已知动词的不重复子集；要能被收银台连接就必须包含 lookup
}

## 2. 鉴权

除 /api/manifest 外，下列接口都要求请求头携带 X-Staff-Key: <密钥>。
密钥由环境变量 STAFF_KEY 配置；用恒定时间比较校验。
- 未携带密钥 → 401；携带但错误 → 403。
- 响应统一为 { "ok": false, "code": "FORBIDDEN", "message": "无效的工作人员密钥" }。

## 3. 业务接口（全部需要 X-Staff-Key）

成功响应一律 { "ok": true, "data": ... }；失败一律 { "ok": false, "code": "大写下划线错误码", "message": "中文可读提示" } 并配恰当 HTTP 状态码。

a) POST /api/call，请求体 { "action": "lookup", "payload": { "code": "..." } }
   查询核销码：存在 → data 为该记录（至少含 code、prize、status）；
   不存在 → 404 + { ok:false, code:"NOT_FOUND", message:"未找到此活动的核销码，请核对" }。
   ⚠️ 重要约定：对一个全 0 的 16 位探测码 "0000000000000000" 必须返回上面的 NOT_FOUND——收银台连接时用它验证密钥，绝不能把它当成真实中奖码。

b) POST /api/call，请求体 { "action": "redeem", "payload": { "code": "..." } }
   核销：成功 → data 为更新后的记录（status 变为 "redeemed"）；
   重复核销 → { ok:false, code:"ALREADY_REDEEMED", message:"此奖品已核销，请勿重复发放" }；
   不存在 → 同 lookup 的 NOT_FOUND。核销必须幂等且并发安全（同一码并发核销只能成功一次）。

c) GET /api/admin/records → data = { "summary": {...汇总...}, "records": [ {...}, ... ] }
   records 每项是一个对象，字段名与 manifest.display.recordFields 的 key 对齐。

d) GET /api/admin/records.csv → 200 text/csv; charset=utf-8，导出全部记录（带 BOM 以便 Excel 打开）。

## 4. 其它要求

- 监听 PORT 环境变量（默认 8787），绑定 127.0.0.1 即可（生产环境前面由 nginx 终结 HTTPS）。
- 核销码比较前先去空白并转大写。
- 记录可以保存在内存或 SQLite/文件中（写明取舍）；提供 GET /health 返回 {ok:true}。
- 任何日志都不得输出密钥明文。

## 8. 附录：协议版本

- **v1（当前）**：连接 = 在服务地址表单里粘贴一次工作人员密钥。
- **v1.1（规划）**：改用一次性配对码换取密钥，免粘贴长密钥。收银台桥接代码已把"换取密钥"隔离成独立一步，届时只需替换该步骤，协议其它部分不变。
