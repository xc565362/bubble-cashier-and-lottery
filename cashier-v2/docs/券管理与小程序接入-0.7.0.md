## 收银员使用

1. 底部「券管理」→「创建券活动」，设置名称、面额、最低消费金额、数量和有效期。
2. 「发券」可手工生成一张券，用于联调或指定发放；领取人标识和发放记录号要保留。同一活动后台的同一中奖记录不会重复发券。
3. 「发放记录」查看可使用、使用中、付款待核实、已核销、已过期、已作废，支持按活动和状态筛选。
4. 收银时先加商品，再扫描顾客中奖券二维码。购物车显示独立优惠行，每单最多一张，不和原有本地优惠券叠加。
5. 点击「收钱吧收款」，勾选确认并发起，扫码盒继续扫顾客付款码。中奖券码和付款码是两个不同的码。
6. 收钱吧核实收款成功后记录订单、扣库存并核销券。优惠后为 0 元时使用「确认零元结算」，不向收钱吧发送零元扣款请求。

使用门槛按单品优惠后的商品应收金额计算；抵扣最多到应收金额，不找零，不形成负订单。赠品没有商品金额。尚未到使用时间的券不能抵扣。

暂停活动仅停止继续发券，已发券仍遵循原有效期；券金额、门槛、有效期发出后不更改，需要调整时创建新活动。作废仅允许对未占用的可用券操作，并记录原因。

扫码盒须支持二维码、键盘输入模式和结束符。界面手工输入也可使用。真实 USB 硬件尚未实测。

## 取消、断网和退换货

- 扫码成功先「占用」，不是立刻永久作废。购物车移除该券会释放占用；扫码后 15 分钟仍未进入支付，服务端在下次访问时释放占用。
- 支付发出后，券进入「付款待核实」，不会按超时时间自动释放。只有核实失败或确认根本没有发起扣款才允许释放。
- 已扣款、但核销同步网络失败时，本机保留待同步记录并重试，券保持占用，不能再次用。不能因券网络报错把实际成功收款当成失败。
- 刷新/重启后会恢复未完成的券零元结算，避免同一券重复扣库存。零元订单核销与本地订单都保存后才结束处理。
- 云端断网时不允许新中奖券优惠，不会悄悄改用本地券库。原有普通商品收银不依赖券中心；未完成的资金交易仍按原有规则锁定。
- 含中奖券的购物车暂不直接挂单，先移除券，取单后重新扫码。
- 正金额中奖券订单仅走收钱吧验签确认收款，不接受静态收款码的手工确认捷径。
- 退款按原实际支付金额分摊，**已核销券不会自动恢复**。零元券订单可取消恢复商品库存，但不能直接改价换成另一笔收费订单；需要重新开单。
- 「券管理→小程序接入→本机占用/待同步」可查询、重试，或释放后台确认未进入扣款的占用。支付结果不明不能强制释放。

## 架构与上线约束

```text
消费者小程序 → 同事的抽奖后台/云函数 → 唯一券中心服务 + 持久数据库
                                        ↑
收银网页 / Windows / Mac → 本机收银服务 ───┘
                            ↓
                          收钱吧
```

- 一个券中心对应一个经营主体。多台收银机连接同一中心，用不同终端凭证实现互斥占用；不支持把不同商户混在一个中心。
- 本版是商家自己承担优惠的店铺券，不是微信官方现金红包或官方立减金，不会由微信/收钱吧补贴金额。
- 券中心接口只供后台调用。小程序前端不能保存管理密钥、发券密钥或收银密钥，不能自行传优惠金额、中奖结论或领取人身份。
- 小程序用户身份必须由其可信后端从微信登录上下文获取。前端传入的 openid、owner、金额、awardId 均不能直接信任。
- 发券前抽奖后台必须验证中奖记录确实属于该用户、奖品类型正确、未撤销，并将中奖记录 ID 作为稳定 awardId。重复调用只得到同一张券。
- 券码是随机签名的持券凭证。可以阻止重复核销，但不能阻止持券人主动转发截图、他人先使用；本版不做动态短时二维码或柜台实名验证。
- 券中心共享券状态，不同步各台电脑的商品、库存和订单库；原有收银数据备份迁移规则保留。
- 正式服务必须长期在线，收银电脑使用网络即可，不要求收银电脑自己暴露公网服务。HTTPS 域名、证书、云平台和小程序发布配置须按实际云环境完成。

## 可部署服务

文件：`coupons/store.cjs`、`http.cjs`、`server.cjs`，依赖 Node.js 24 LTS 的内置 SQLite，无需 npm 安装数据库模块。

环境变量：

| 变量 | 要求 |
| --- | --- |
| `COUPON_ADMIN_TOKEN` | 至少 32 字符，允许字母、数字、下划线、点、连字符；建议 32 随机字节生成 64 位 hex |
| `COUPON_DATA_DIR` | 私有持久数据目录，不能是网站静态目录或临时目录 |
| `COUPON_ENV` | 正式库为 `production`；缺省 `development`，两种库不能混用 |
| `HOST` | 默认 `127.0.0.1`；容器用 `0.0.0.0` |
| `PORT` | 默认 `3910` |

生成密钥的本机命令（输出要私密保管）：

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

正式部署示例，由部署人员配置环境，不要把示例变量名当密钥：

```bash
docker build -f coupons/Dockerfile -t cashier-coupons:0.7.2 .
docker run -d --name cashier-coupons --restart unless-stopped \
  -p 127.0.0.1:3910:3910 \
  -v cashier-coupon-data:/data \
  --env-file /secure/coupon-production.env \
  cashier-coupons:0.7.2
```

环境文件放 `COUPON_ADMIN_TOKEN=实际密钥`。Dockerfile 已设置正式环境和 `/data`。HTTPS 反向代理把专用域名根路径转发到 3910，限制请求体并加连接/速率保护。不要直接把无 TLS 的 3910 端口暴露公网。`GET /healthz` 只用于存活检查，不代表小程序业务已经接通。

**SQLite 部署限制：本版是单实例、单持久磁盘的事务数据库实现。不能把数据库放到会销毁的云函数临时盘，也不能让多个独立容器各保存一份库，更不能通过网盘文件同步冒充共享数据库。** 若现有环境只有微信云函数/云数据库，收到配置后需要适配那套数据库的事务和唯一约束，不可原样上传后就宣称上线。

配置步骤：部署 HTTPS 服务 → 收银端「云端连接」填域名与管理密钥 → 在正式中心创建券活动 → 「小程序接入」生成该活动的抽奖后台凭证 → 同事配置后台 SDK。

## 小程序后台接口

请求：`Authorization: Bearer <抽奖后台凭证>`，POST 为 `Content-Type: application/json`。

成功：`{"ok":true,"data":...}`；失败：`{"ok":false,"code":"错误码","error":"说明"}`，并返回对应 HTTP 错误码。金额一律整数分，时间为 ISO 8601。默认每个凭证每分钟 180 次请求，需结合实际抽奖人数在网关和服务中配置容量，不要让前端高频轮询。

### 发券

`POST /v1/coupons/issue`

```json
{
  "requestId": "稳定请求ID",
  "campaignId": "券活动ID",
  "owner": "后台验证得到的微信用户标识",
  "awardId": "后台确认的唯一中奖记录ID"
}
```

返回含 `id`、`name`、`amountCents`、`minimumCents`、`startsAt`、`expiresAt`、`state`。仅可用券返回 `code`，用于生成二维码。使用过的券重试发放不会生成新券，也不再返回可用券码。

同一请求编号不能改内容，否则 `IDEMPOTENCY_CONFLICT`；同一活动凭证授权范围内同一 awardId 不能更换用户。轮换同活动凭证不重置中奖幂等性，旧凭证可停用。

### 用户券列表

`GET /v1/coupons?owner=<后台验证的用户标识>&page=1`

返回 `{items,page,total,pageSize:30}`，仅返回该活动后台授权发出的该用户券，不返回所有用户券码。列表无 `code`，点击显示二维码时再调用详情。

### 用户券详情

`POST /v1/coupons/detail`，JSON 为 `{ "id":"券ID", "owner":"后台验证的用户标识" }`。

归属不符返回 403。券状态为 `AVAILABLE` 时可展示二维码；`RESERVED` 显示使用中；`PAYMENT_PENDING` 显示付款待核实；`REDEEMED` 显示已使用；`EXPIRED`、`VOID` 不显示可用码。

二维码页回到前台时重新读状态；展示期间做有频率限制的状态刷新。只读取接口状态，不因为本地倒计时结束自行把券变为可用。

### 后台 SDK

文件 `coupons/lottery-client.cjs`，服务端 Node.js 环境使用。下面只是调用位置示例，`verifiedAward` 必须先通过你同事的抽奖后台校验，不能直接等于用户请求内容。

```js
const { createLotteryClient } = require('./lottery-client.cjs');
const coupons = createLotteryClient({
  baseUrl: process.env.COUPON_URL,
  token: process.env.COUPON_LOTTERY_TOKEN,
  campaignId: process.env.COUPON_CAMPAIGN_ID,
});

// After authenticating the WeChat user and verifying their persisted win:
const coupon = await coupons.issueForVerifiedAward({
  owner: verifiedAward.owner,
  awardId: verifiedAward.id,
});
// A user's wallet must use the authenticated server-side owner:
const wallet = await coupons.listForAuthenticatedOwner(authenticatedOwner);
const detail = await coupons.detailForAuthenticatedOwner(authenticatedOwner, couponId);
```

`COUPON_LOTTERY_TOKEN` 只能配置在后台环境变量/密钥管理中。前端调用自己的云函数/服务器，后台再调用这些接口。不要把返回对象中的 issuer、内部锁券信息无筛选转给前端；只映射页面实际需要的券字段。

管理接口有活动增建/暂停、凭证创建/停用、作废及事件记录；收银专用接口有占用、准备支付、核销、释放。抽奖后台凭证无权调用管理或收银接口，前端也不会暴露这些操作。

## 数据、安全和迁移

- 正式数据库 `coupons.sqlite` 和其 WAL/SHM 文件仅保存在云端持久数据目录，备份责任在云端。数据目录同时含券签名材料，要做权限控制和加密备份。
- 不要在线直接只拷贝主 `.sqlite` 文件。使用 SQLite 一致性备份，或停服务后完整备份私有数据目录。恢复历史库可能使已核销券重新出现，必须停发券/停用券，并与收钱吧、本机订单、发放记录对账后再恢复营业。
- 收银端经营备份不含云端券库或云端服务密钥。更换电脑先处理完未决支付和占用，再迁移经营数据、收钱吧加密配置，在新电脑连接同一券中心获得新的终端凭证。
- 本机保存 `coupon-connection.json`、`coupon-transactions.json`；桌面端使用现有系统安全存储加密凭证，网页版依赖本机目录权限。不要公开复制这些文件，也不要在未决交易时删除它们。
- 本机券状态不允许通过经营备份回滚云端核销。未完成占用/核销时禁止导出/覆盖经营备份。
- 当前没有独立管理员登录/多角色员工后台，本机已授权操作员可管理券，勿把收银本机管理服务暴露互联网。

## 上线验收清单

1. 确认云环境持久化方式、HTTPS 域名、备份与日志权限，确认不会部署多个相互独立的券库。
2. 用真实微信登录验证：中奖用户只能取自己的券，没中奖的用户不能伪造 awardId 领券。
3. 同一中奖记录重试只得一张券；两台收银机同时扫同一券只有一台成功。
4. 实机扫码盒能读券二维码；支付时能读顾客付款码并输出结束符。
5. 正式环境小额验收：优惠后实收金额、商户到账、收钱吧流水、券状态、库存都一致。操作前明确知晓会真实扣款。
6. 取消、未知支付、断网重连、零元结算、退款不自动退券分别验收。
