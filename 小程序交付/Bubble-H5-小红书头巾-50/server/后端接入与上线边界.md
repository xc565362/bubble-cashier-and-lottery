# 山野有约：H5与收银接入

2026-10-08 本地实现。尚未部署云函数、启用正式活动、修改真实库存或验证真实微信登录。默认魔术头巾200份，单次50%，日期待配置。

## 业务与切换边界

- 活动编号固定 `scarf-xhs-50-v1`，独立于原抽奖活动。工作人员确认关注后，生成最长10分钟、仅一次使用的参与小程序码。同一个微信OpenID只能抽一次，中奖/未中奖都持久化。服务端以0至9999均匀随机整数和 `winProbabilityBps` 比较，5000为50%，允许0至100%。库存0时停抽并保留未使用资格。
- 收银管理支持暂停、恢复、奖品名称/HTTPS图片、商品绑定、概率、累计名额与日期。暂停后才能改配置，名额不能少于累计中奖份数；日期全空可保存草稿，恢复前必须补齐。商品至少有一个SKU或条码。
- 新中奖由券中心生成16位大写十六进制实物券。收银台扫码、生成数量1单价0的领奖订单，完成后扣一次本机库存。H5同步核销结果，不能直接核销此类奖品。
- 更换SKU/条码或权益期限自动创建新奖项ID，老中奖保留原奖品/商品/有效期。改名和图片也不覆盖历史快照。累计名额不等于收银库存；商品库存不足仍会拒绝核销，不同收银电脑的本地库存不会自动同步。
- 升级前独立领取码为 `legacy`（无字段的旧记录也按legacy），继续通过原H5工作人员工作台核销，**不会自动导入券中心，不能在收银台兑换**。切换先暂停，保存配置和商品绑定，核对券中心后恢复；随后新中奖为 `cashier`。
- cashier奖的H5 redeem永远返回 `USE_CASHIER`，防止两处重复发奖。收银管理暂停只停止新抽奖，已有新券与旧legacy码仍按原期限核销。旧码不得人工复制为新券或清空中奖记录。原未接管理的独立活动仍保留自身暂停核销规则。

## 云端准备

1. 在已授权并与 `wx3cfec968f30fb6c1` 关联的云环境部署 `cloudfunctions/bubble-scarf-gateway`；Node运行时须有全局fetch，依赖沿用package中的固定版本。实际HTTP映射/事务行为仍需联调。
2. 创建仅服务端可读写集合：`bubble_scarf_campaigns`、`bubble_scarf_inventory`、`bubble_scarf_entries`、`bubble_scarf_invites`、`bubble_scarf_codes`、`bubble_scarf_rates`、**`bubble_scarf_management`**。全新活动可由收银端首次保存原子创建，无需手动初始化。已有活动不要覆盖示例或重置库存。
3. 参照environment.example.txt配置H5登录/允许域名/工作人员名单。H5_TOKEN_SECRET与SCARF_MANAGEMENT_KEY分别生成独立32字节随机值的64位hex；管理key为小写hex。AppSecret、管理key、券中心令牌只存服务器或对应受保护本机存储，不下发H5。
4. SCARF_COUPON_URL、SCARF_COUPON_CENTER_ID、SCARF_COUPON_ADMIN_TOKEN指向与收银系统相同的生产券中心，要求 `lottery-catalog-v1`、实物券、扩容接口。云函数入口只允许生产HTTPS；localhost HTTP仅供createScarfCenter的显式allowLocalTest隔离测试。
5. 映射 `POST /api/scarf-management` 并设置SCARF_MANAGEMENT_ENABLED=1。收银端填写完整HTTPS管理地址、活动编号和SCARF_MANAGEMENT_KEY；不要把券中心管理员令牌填进收银表单，也不要把H5 /call当成管理地址。
6. H5 `/api/scarf-h5/session`、`/call`、小程序原生 `pages/scarf-h5/index`、业务域名/微信登录/生成码权限按原integrations接入说明处理。参与码为已正式发布入口的release小程序码；服务不直接查询小红书关注状态。
7. 独立测试环境验收后设H5_BACKEND_REVIEWED=1、H5_GATEWAY_ENABLED=1；收银保存奖品/商品/日期后恢复活动。环境变量改变后需部署/重启刷新缓存。不要在已有活动中随意换券中心；首次中心身份永久保留，即使把日期清空也不解除绑定。

可设置TTL：management.expiresAt只用于签名nonce；rates.expiresAt和invites.deleteAfter用于限流/过期邀请。管理幂等操作、中奖、领取码和库存不得清理。管理操作记录没有expiresAt，不能用集合级统一过期规则清掉。

## 管理接口协议

请求体 `{campaignId:'scarf-xhs-50-v1',action,payload}`。头为X-Lottery-Time（13位毫秒）、X-Lottery-Nonce（唯一UUID）、X-Lottery-Signature。

签名 `HMAC-SHA256(key, time + '\n' + nonce + '\n' + 原始JSON)`，结果小写hex。**key按64字符文本使用，不转32字节**，与payments/lottery.cjs一致。允许60秒时差，以事务拒绝nonce重放；拒绝任何带Origin的浏览器请求。成功 `{ok:true,data}`，失败 `{ok:false,code,error}`。

- snapshot：payload `{}`。响应 `{service:'bubble-scarf-management',version:1,campaignId,revision,campaign,prize,inventory,fulfillment,audit}`。
- update：payload `{revision,requestId,operation,reason}`，operation为pause/resume/configure，reason必填。requestId为8至100位字母/数字/下划线/横线，相同请求可重复而不再改一次，同requestId不同内容被拒，旧revision返回REVISION_CONFLICT。
- configure额外传 `campaign:{title,venue,startsAt,endsAt,redeemEndsAt,winProbabilityBps}`、`prize:{id,name,imageUrl,product:{id,name,sku,barcode}}` 和total。日期接受ISO或毫秒，响应为毫秒；全null为草稿。imageUrl空时沿用黄橘头巾图，否则必须HTTPS。服务端决定prize.id，前端不能重绑历史权益。
- inventory为total/remaining/awarded/redeemed，total是活动累计名额。fulfillment为ready/centerId/environment；ready代表中心可用，不能替代日期和商品配置校验。audit保留最近100次原因、操作、revision及关键前后值，独立幂等记录长期保存。

配置先幂等准备券中心活动，再以revision提交本活动；并发失败可能留一份未发券的券中心准备活动，只有最终提交的映射能开奖。不要手工发放未使用的准备活动。

## H5与发券状态

H5继续用Bearer token认证，允许state/draw/identity/grant/lookup/redeem六个动作，无管理权限。state返回当前campaign/prize、entry快照和inventory/availability；商品内部ID、管理凭证、OpenID不会传给H5。

entry状态为lost、issuing、pending、reserved、redeemed、expired，仅pending返回code；fulfillment为cashier/legacy，fulfillmentStatus为ready/pending/legacy。查询券中心失败也会隐藏旧码，显示issuing并自动重试；reserved为收银结算占用中。未中奖不访问券中心。

事务先固定结果、奖品快照、名额、邀请码及领取码，再在事务外幂等发券。发券成功但响应丢失仍重试同一awardId/code，不重抽；券中心核对活动、领取人哈希、中奖ID和原码，响应再校验商品/权益归属。查询核销结果时本地计数只增加一次，管理快照亦合并所有历史券活动的已核销数量与legacy计数。

中心身份验证缓存60秒并合并并发请求，请求失败清缓存；每张券状态仍通过专用详情接口查询。同步失败不会释放中奖名额或再次发奖。日志禁止记录密钥、OpenID、登录凭证、邀请码和领取码。
